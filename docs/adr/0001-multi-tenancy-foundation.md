# ADR-0001 · Фундамент мультитенантности

- **Статус:** Принято
- **Дата:** 2026-06-20
- **Контекст:** приложение эволюционирует из однотенантного (один вуз, одна конференция) в облачный multi-tenant SaaS для вузов РФ.

## Решение

- **Иерархия:** `Organization` (тенант = вуз) → `Conference` (событие) → данные события (Section, Room, Slot, доклады, регистрации, документы, чат, Q&A). Конфиг бренда/домена/биллинга — на уровне `Organization` (`org_id`); данные события — на уровне `Conference` (`conf_id`, всегда принадлежит одному `org_id`).
- **Идентичность:** глобальный аккаунт пользователя (единый вход) + `Membership` (роль и профиль) на каждый тенант.
- **Изоляция данных:** shared-DB + shared-schema + `tenant_id` (`org_id`/`conf_id`), enforced **тремя барьерами**: резолвинг тенанта → request-scoped GORM-scope → Postgres Row-Level Security (fail-closed). Забытый WHERE возвращает 0 строк, а не чужие данные.
- **Резолвинг тенанта:** по поддомену (`Host`), сверка с org-claim в JWT и активным членством. Внедряется в Фазе 2.

## Следствия

- Каждая таблица данных тенанта получает явный ключ скоупинга (Фаза 1).
- Обязательный CI-гейт кросс-тенант-изоляции на реальном Postgres (RLS в SQLite не существует).
- Фазы: Ф0 страховка → Ф1 фундамент (колонки+backfill) → Ф2 резолвинг+enforced scoping (RLS).
